# Padock — Core Concept

> Status: v0.8 — Phase 0 through 9 shipped (platform skeleton → thin vertical slice → CLI → universal Skill → deepened domains → MCP transport → PAT granular scopes → approval queue for unattended agents → web UI shell → chat/task/doc web UI → project access control + deepened task model + multi-view task UI). The §8 north-star scenario runs end-to-end for both interactive/non-interactive agents (CLI/MCP) and, as of Phase 8, for a human working directly in the browser too. Phase 9 (§5.1.13–§5.1.15) turned `Project` into a real membership boundary — a project's data (tasks/docs/its channels) is only visible to its own `ProjectMember`s, not every org member — and deepened `Task` with priority/dates/multi-assignee plus five view layouts (List/Board/Table/Calendar/Timeline) on the project workspace's Task tab. Remaining work is explicitly deferred, not blocking (§7) — see §9 for the full phase-by-phase record. Update this file as decisions solidify; do not let it drift from reality.

## 1. One-liner

Padock is an open-source, self-hosted, **agent-first workspace** for SMEs that unifies team communication, task/project orchestration, and document management into one platform — plus a CLI + Skill layer that lets subscription-tier AI agents (Claude Code, Codex, Gemini CLI, etc.) operate the whole workspace on the user's behalf.

## 2. Problem statement

- AI is spreading fast inside SMEs, but most non-technical staff and even most technical staff use **subscription products** (Claude Pro/Max via Claude Code/Desktop, ChatGPT/Codex, Gemini) rather than pay-per-token API access.
- Subscription-tier agents are functionally locked into their official surfaces (chat UI, Claude Code, Codex CLI, Gemini CLI). There is no standard way for them to reach into a company's actual working systems — chat, tasks, documents — without someone building bespoke API integrations per tool, per company.
- Meanwhile SME operational data is fragmented across separate SaaS silos (chat app, task tracker, docs tool), each with its own auth, its own UI, and no shared "agent" concept. A person doing real work ("find X in project Y, analyze it, send it to a colleague, mark the task as review") has to manually hop between three tools; an agent today mostly can't do this at all unless someone pays for API access and wires up custom integrations per company.
- Padock's bet: if the workspace itself is **agent-native** (not "human app with an API bolted on") and ships a CLI + Skill that any subscription agent can pick up, SMEs get end-to-end agentic workflows without needing API-token billing or custom integration work.

## 3. Target users (TA)

Small-to-medium enterprises (中小企業) — teams too small to have a platform/integration engineering function, currently using disconnected SaaS tools, whose staff (technical and non-technical) primarily access AI through subscription products rather than API keys.

## 4. Core concept: agent-first workspace

"Agent-first" means the workspace's data model and APIs are designed so an **agent is a first-class actor**, not a UI convenience layered on top of a human-only app:

- Every meaningful operation (search, read, post message, change task status, create/edit doc) is exposed as a structured, scoped, auditable **action** — not just inferred from UI clicks.
- Actions are composable across domains: an agent should be able to chain "search across chat+tasks+docs → analyze → confirm with human → act → update state" in one flow, the way the motivating example describes:
  > "幫我去某某專案找某某資料，整理分析完之後告訴我，確認沒問題請幫我發給某某同事，然後把任務狀態改成 review。"
- Every agent action is attributable (which agent, on whose behalf, under what permission scope) and logged — SMEs need to trust what an autonomous agent did inside their real workspace.
- Irreversible/outward-facing actions (sending a message, closing a task) default to a **confirm-before-act** pattern, matching the example scenario's own "確認沒問題請...". For interactive agents this is just the agent's own conversation turn, not server-side infrastructure — the human confirming in natural language *is* the confirm-before-act mechanism. For non-interactive/scheduled agents (no human present to confirm live), Phase 6b adds a server-side approval queue as the equivalent mechanism (§5.1.1, §6): a flagged PAT's writes queue instead of executing, until a human decides on the web `/approvals` page.

## 5. System architecture (proposed)

Three native subsystems, one shared platform, one integration layer that reaches out to external subscription agents.

### 5.1 Padock Workspace (the product)

Self-built, not third-party integrations:

- **Chat** — team communication, channels/threads, DMs. Reference: Zulip (threaded conversation model).
- **Task/Project orchestration** — issues, projects, status workflows. Reference: Plane (open-source Jira-like model).
- **Document management** — knowledge base / docs, block-based content. Reference: AFFiNE (local-first, block model).
- Shared services: Postgres (system of record), Redis (cache/pubsub/queue, needed for chat realtime), object storage (S3-compatible, e.g. MinIO, for files/attachments).

**Architecture: modular monolith, multi-process deployment.** One TypeScript codebase; chat/tasks/docs are internal modules (folder boundaries + internal interfaces, no bypassing each other's data layers), sharing one Postgres schema. Deployed as multiple *process roles* from the same codebase — the same pattern Plane (Django: api/worker/beat) and Zulip (Django + Tornado realtime) use:

- `app` — Next.js web UI + tRPC API (the T3 core)
- `realtime` — standalone lightweight WebSocket gateway: manages long-lived connections, receives events via Redis pub/sub, pushes to clients. No business logic lives here.
- `worker` — background jobs (BullMQ or similar over Redis)

This is explicitly **not** domain microservices (no separate chat-service/task-service/doc-service): cross-domain search and transactions (§8) stay cheap, one version number for self-hosters, one repo for contributors. Redis pub/sub is the deliberate seam — if a domain or the realtime gateway ever needs to be extracted or horizontally scaled, the transport is already in place.

### 5.1.1 Tech stack: T3 + Turborepo

Core stack is the **T3 stack** (Next.js, tRPC, Tailwind, Better Auth, Prisma) inside a **create-t3-turbo-style Turborepo**:

```
apps/
  web/        # Next.js (T3): UI + tRPC API — the `app` process role
  realtime/   # ws gateway — the `realtime` process role
  worker/     # background jobs — the `worker` process role
  cli/        # padock CLI (see §5.2)
packages/
  api/        # tRPC routers (chat/tasks/docs modules live here)
  db/         # schema + ORM client
  auth/       # shared auth logic
  ...
```

Key property: the CLI imports the tRPC client and gets **end-to-end type safety** — an API signature change breaks the CLI at compile time, which matters for long-term OSS maintenance. tRPC is an internal contract, not a public third-party API; all first-party consumers (web, CLI, MCP wrapper, Skills) are TypeScript. If non-TS third-party clients are ever needed, generate a REST layer (e.g. trpc-openapi) then — not a v1 cost.

**How the CLI consumes tRPC** (tRPC is plain HTTP underneath; `@trpc/client` runs in any Node process):

- CLI uses `createTRPCClient<AppRouter>` + `httpBatchLink` pointed at the self-hosted instance's `/api/trpc`; `import type { AppRouter }` is type-only — no server code in the CLI bundle.
- **Auth: Better Auth**, not Auth.js (NextAuth) — Auth.js entered maintenance-only mode in early 2026 when Better Auth absorbed the project (security patches only, no new features); Better Auth itself was acquired by Vercel in July 2026 and is under active development, including an "Agent Auth" protocol for AI agent identity — directly adjacent to this project's own agent-attribution needs (§4). Better Auth is also framework-agnostic, which matters because `realtime`/`worker` are plain Node processes, not Next.js apps, and need to validate the same identity without a Next.js request context. A shared `packages/auth` instance (Prisma adapter) is mounted by `apps/web` and imported directly by `apps/realtime`/`apps/worker`.
- **Dual-track auth**: browser sessions use Better Auth's session cookies; the CLI uses Better Auth's official **API Key plugin** as its Personal Access Token (PAT) mechanism (`padock login` → key stored in `~/.config/padock/`, sent as an `x-api-key` header — the plugin's default). Verified against the real package: Better Auth *can* auto-mock a session from an API key (`enableSessionForAPIKeys`), but that flag is off by default and explicitly documented as not production-safe — so our tRPC context resolves identity explicitly instead: try `auth.api.getSession()` (cookie) first, then fall back to `auth.api.verifyApiKey()` against the `x-api-key` header, both collapsing into one context shape. This replaces a hand-rolled PAT table/middleware, and the API Key plugin supports per-key scoping if/when granular agent permissions (§7) are needed later.
- **Organization plugin** (official) gives roles/membership within the single-tenant org (§6) without hand-rolling a membership table.
- **v1 login flow**: manual token copy — user generates an API key from the web UI's settings page, pastes it into `padock login --token=<key>`. No device-code flow in v1 (that's an OAuth Device Authorization Grant implementation cost not justified before there's a multi-user, non-technical audience actually hitting friction here).
- **PAT granular scopes — done (Phase 6)**: per-domain `read`/`write` scopes (`project`, `task`, `taskState`, `doc`, `chat`, `channel`, `topic`, `user`, `search`), mapped 1:1 onto tRPC's query/mutation split via a `scopedProcedure(resource, action)` builder in `packages/api/src/trpc.ts`. Stored in the API Key plugin's existing `permissions` column (`Record<string, string[]>`, verified against the real `@better-auth/api-key` package — no schema migration needed). `permissions: null` (every key issued before this phase, and any new key created without `--scope`) stays **unrestricted**, so nothing existing breaks. Key issuance (`apikey.create`) is gated behind a **session-only** procedure — no API key, scoped or not, can mint another key, closing the self-escalation path outright. Finer granularity (per-project, per-verb) is deferred — not needed yet. One real constraint surfaced during verification: the CLI's name-based resolution (`resolve.ts`'s `resolveProjectId`/etc.) always calls the target domain's own `list` procedure first, so a scoped key needs `project:read` (and similarly `channel:read` for topic resolution) as a practical baseline alongside whatever domain it's actually meant to touch.
- **Approval queue for unattended agents — done (Phase 6b)**: a PAT can be flagged `unattended: true` at creation (stored in the API Key plugin's `metadata` field — required enabling `enableMetadata: true` on the plugin config, off by default, discovered when key creation failed with "Metadata is disabled"). Every write such a key attempts is queued as an `ApprovalRequest` row (`path` = the dot-joined tRPC procedure path, `input` = the validated call input) instead of executing, via `runOrQueue()` (`packages/api/src/approvalGate.ts`) called as the first line of each write resolver's body — not a `.use()` middleware, since tRPC v11 middleware can only `next()` or `throw`, never fabricate a successful response (its `MiddlewareResult`'s `marker` field is branded with an unexported internal symbol — verified by reading the installed `@trpc/server` source, not assumed). A human reviews/decides on a new web page (`/approvals`, session-only, first real UI page beyond the Phase 0 debug page) or the agent polls its own submissions via `padock approvals status <id>`/`list`. Approving replays the exact stored call through `appRouter.createCaller`/the exported `callTRPCProcedure` helper, as the *original key's owner* with full access (a human already reviewed the content, so re-checking the original resource scope adds friction, not safety) — critically with `unattended: false` on the replay identity, otherwise the replay would re-queue itself instead of ever executing. Reads are never gated. No expiry/TTL on pending requests in v1.
- **Enterprise directory login (LDAP)**: no raw LDAP bind in v1. Better Auth has no official LDAP plugin (a feature request for one was explicitly closed "not planned" by the maintainers; only an unofficial community plugin exists). The supported enterprise-auth path is Better Auth's official **SSO plugin** (SAML/OIDC) — the realistic modern pattern is fronting AD/LDAP with an identity provider (Entra ID, Okta, or self-hosted Keycloak, which itself can bridge to LDAP) rather than Padock speaking raw directory protocol. Revisit direct LDAP bind only if a real deployment needs it and the SSO path proves insufficient.
- **Version skew guard**: compile-time type safety doesn't protect a newer CLI against an older self-hosted server. CLI and server release together from the monorepo under one version; the CLI does a version handshake (`GET /api/version`) and warns on mismatch.
- **Origin header requirement (verified in Phase 0)**: Better Auth rejects state-changing requests (sign-up, sign-in, API key creation, etc.) with `MISSING_OR_NULL_ORIGIN` unless an `Origin` header matching a trusted origin is present — true even for non-browser clients. The Phase 2 CLI must send `Origin: <server base URL>` on every request that hits these endpoints.

### 5.1.2 Cross-domain data model: the Project/Space entity

`§8`'s scenario filters across all three domains with `--project=某某專案`, which only works if chat/tasks/docs share a common anchor. Padock defines a single `Project` entity from day one (not deferred to a later phase — retrofitting it once chat/task/doc data already exists without a project reference would be a heavy migration):

- **Tasks** belong to exactly one `Project` (required foreign key).
- **Docs** belong to exactly one `Project` (required foreign key) — v1 has no folder hierarchy beyond this.
- **Chat** shipped DM-only in Phase 1 (see §5.1.3); Phase 4 added Zulip-style channels + topics. A DM can optionally carry a `project_id` tag — set by a human or agent when a DM is "about" a project. A **channel** can itself optionally belong to a Project (its messages inherit that project context; they don't carry their own tag). `--project=X` search spans docs + tasks (always project-scoped) + any project-tagged DMs + any messages in a project-scoped channel (opt-in either way).

### 5.1.3 Module scope for Phase 1 (confirmed)

- **Chat**: point-to-point DM only. No channels, no threads, no unread state — just send/read a message between two accounts. Enough to validate step 4 of §8 ("發給某某同事"). Messages can optionally carry `project_id` (§5.1.2).
- **Task** shipped Phase 1 with a fixed status enum (`todo`/`in_progress`/`review`/`done`), no custom workflows. Phase 4 replaced this with per-project configurable states — see §5.1.5.
- **Doc**: stored as plain Markdown text, not block-based JSON. `padock doc get <id>` returns Markdown directly — the most LLM/agent-readable format, and the cheapest to build. The long-term AFFiNE-style block model is a storage-layer migration (Markdown → blocks) for later; it does not change the CLI/Skill contract, since agents will keep consuming readable text either way.
- **Search**: Postgres full-text search (`tsvector`), not semantic/vector search. No embedding model or extra API dependency — consistent with the "no API token required" premise. Padock returns precise keyword/metadata matches; semantic interpretation of results is left to the calling agent's own LLM reasoning, not to Padock's search layer. Revisit only if keyword search proves insufficient in practice.

### 5.1.4 Chat channels/threads (Phase 4, shipped; superseded by §5.1.10)

> **Superseded (Phase 8, done):** the two-level `Channel`→`Topic` structure described below has been collapsed into a single `Channel` level — see [ADR-0001](docs/adr/0001-collapse-topic-into-channel.md) and §5.1.10. `Topic` no longer exists as a database table or a CLI/MCP concept. This section is kept as the historical record of what Phase 4 actually shipped.

Zulip's stream+topic model (§5.1's reference), not Slack's channel+reply-thread model: a `Channel` contains named `Topic`s, and every message belongs to exactly one topic. A `ChatMessage` is now either a DM (`recipientId` set) or a channel message (`channelId`+`topicId` set) — never both.

- **Channels can be org-wide or project-scoped** (`Channel.projectId` optional) — not one or the other. Same opt-in-tag pattern as a DM's `project_id` (§5.1.2), just one level up: a channel's project context applies to all its messages instead of being set per-message.
- **No per-channel membership/subscription model in v1** — consistent with §6/§7's "no granular permissions yet" stance. Every org member can read every channel/topic; there's nothing to join or be excluded from. Real per-channel access control is deferred to the same future bucket as granular agent permissions (§7), not invented piecemeal here. DMs remain private to their two participants (enforced at the query layer, unchanged from Phase 1).
  > **Partially superseded (Phase 9, done):** this stance is reversed for *project-scoped* channels only — see §5.1.13. Org-wide channels (`projectId` null) are unaffected and stay open to every org member exactly as described above.
- **Realtime broadcast is unfiltered** — `apps/realtime`'s WebSocket gateway (built Phase 0, unused until now) broadcasts every chat event (DM or channel) to every connected authenticated socket, no per-channel/per-DM filtering. A client's actual read scope is enforced by `chat.history`/`conversation`/`search`, not the push layer — the push is a "something changed, go re-fetch" signal, not a delivery-scoped feed. This is the first real use of the Redis pub/sub seam §5.1 named as the future extraction/scaling point.

### 5.1.5 Task workflows (Phase 4, confirmed)

Plane's actual model (the named reference), replacing Phase 1's fixed `TaskStatus` enum: each `Project` defines its own set of `TaskState`s instead of every task sharing one global enum. A state has a `name`, a semantic `group` (`backlog`/`unstarted`/`started`/`completed`/`cancelled` — Plane's own five categories, so reporting/search can reason across projects even when state *names* differ), a `position` (ordering within that project's workflow), and `isDefault` (which state a new task lands in).

- **Configurable state sets, not configurable transition rules.** Plane itself doesn't hard-enforce which state can move to which — the configurable part is *what states exist* in a project, not a transition-validation engine. Building transition rules here would be scope creep beyond what "Plane-style configurability" actually names.
- **Every project is seeded with six default states on creation** (Backlog/Todo/In Progress/In Review/Done/Cancelled, "Todo" as default) so it's immediately usable — not stuck with zero valid states until someone manually configures a workflow. Projects can add their own states beyond these (`task-state create`).
- **`padock task update <id> --status=<name>` resolves the name against that task's own project's states**, not a global enum — the CLI looks the task up first (`task.get`, new in Phase 4) to find its project, then resolves. Two different projects can have identically-named states (e.g. both defining "Blocked") without conflict — `TaskState` is unique per `(projectId, name)`, not globally.

**Migration note (real, not hypothetical — Phase 4 shipped with live dogfood data in play):** Phase 1's two existing tasks had non-null `status` values. Dropping that column required an explicit two-step schema change (add `TaskState`/optional `stateId` first, backfill, then drop `status`/`TaskStatus`), not a single blind schema push. This is what prompted the tooling change below.

### 5.1.6 Schema tooling: `prisma migrate`, not `db push` (Phase 4, confirmed)

Attempting the `status`-column drop above via `prisma db push --accept-data-loss` triggered Prisma's own built-in AI-agent safety gate: it detected an agent invoking a destructive flag and refused to run without the user's explicit, verbatim consent (a real, current guardrail in the Prisma CLI, not a Padock feature). The user's direction after that: stop using `db push` for schema changes going forward, adopt `prisma migrate` properly.

- The existing `db push`-managed database was **baselined**, not reset: `prisma migrate diff --from-empty --to-config-datasource --script` captured the live database's actual current state as `migrations/0_init`, then `prisma migrate resolve --applied 0_init` recorded it as already-applied without executing anything — zero data touched by this step.
- New schema changes now go through a real migration file, generated via `prisma migrate diff` (comparing the live database against the target `schema.prisma`) and reviewed as a diffable `.sql` file before being applied with `prisma migrate deploy` — not blind `db push --accept-data-loss`. The Docker `app` image's boot command changed to match (`prisma migrate deploy`, not `db push`).
- This is a real workflow change, not a one-off: every future schema change goes through this same generate-review-apply sequence.

### 5.1.7 Doc block-based storage (Phase 4, confirmed)

Replaces Phase 1's plain-Markdown-text storage, per the migration §5.1.3 always named as coming. **mdast (Markdown AST, from the `remark`/`unified` ecosystem) is the block tree — not a bespoke block schema.** mdast already models a document as a tree of typed blocks (`heading`, `paragraph`, `list`/`listItem`, `code`, `blockquote`, ...); that's what "block-based storage instead of a raw text blob" means, so there was nothing to invent. `Doc.blocks` stores the parsed tree (`Json`); `Doc.searchText` is a plain-text extraction of it (`mdast-util-to-string`), kept only so full-text search stays a normal Postgres `text` column instead of reaching into JSON at query time.

- **The CLI/Skill contract is unchanged, verified rather than assumed** — `packages/api/src/router/doc.ts` parses incoming Markdown to `blocks` on write and stringifies `blocks` back to Markdown as `content` on every read (`get`/`list`/`create`/`update` all return `content`, never `blocks`/`searchText`). Confirmed zero files touched under `apps/cli/` or `apps/cli/skill/` for this phase.
- **Round-tripping is structurally, not byte-for-byte, identical.** `remark-stringify` normalizes on the way back out — e.g. `-` bullets become `*`, a trailing newline gets added. Content and meaning are unchanged; exact source bytes are not preserved. This is a real, observed deviation from what the original Phase 1 wording ("agents will keep consuming readable text either way") implied, not a defect — no agent or human reading either version would notice a semantic difference, but it's worth being precise that it isn't a lossless byte-identity guarantee.
- **No custom block types, no CRDT.** Both stay exactly as scoped: a future editor UI needing block types beyond what Markdown expresses would be an additive schema extension on top of mdast, not a reason to have built a bespoke schema now; CRDT/multi-user co-editing remains deferred per §6.

### 5.1.8 Web UI: public shell, auth flow, authenticated shell (Phase 7, confirmed)

Phase 7 built the first real (non-debug) web UI, replacing the Phase 0 debug homepage and giving the product an actual entry point:

- **Landing page** (`/`) — public, unauthenticated entry page with sign-up/log-in CTAs, replacing the Phase 0 debug page.
- **Auth pages** (`/login`, `/register`) — built on the Better Auth React client (`authClient`/`useSession`/`signIn`/`signUp`/`signOut`, `apps/web/src/lib/auth-client.ts`), paired with the shadcn/ui `<Form>` (react-hook-form + zod) adopted as the standing convention (§6, "UI component library").
- **Route protection lives in `proxy.ts`, not page rendering mode** — confirms the §6 "Rendering model" decision. `apps/web/proxy.ts` checks only whether a session cookie is present (`getSessionCookie`, no DB hit) and redirects: signed-in users away from `/`, `/login`, `/register` toward `/dashboard`; signed-out users away from `/dashboard`, `/approvals` toward `/login`. This is a UX redirect only — real authorization still happens server-side per tRPC call (`resolveIdentity`), unchanged since Phase 0.
- **Authenticated app shell** — `(app)/layout.tsx` adds a persistent header (nav links to Dashboard/Approvals, signed-in user's email, sign-out) wrapping both pages. `/approvals` (Phase 6b) now lives inside this shell instead of standing alone. **Superseded (Phase 8, done):** the top-nav header was replaced by a persistent left sidebar — see §5.1.12.
- ~~`/dashboard` is a placeholder, not a real page~~ — **superseded (Phase 8, done):** `/dashboard` is now the real chat feed + project overview described in §5.1.12; chat/task/doc web UI all exist now, not CLI/MCP-only.

### 5.1.9 Chat display boundaries in the web UI (Phase 8, done)

`ChatMessage.projectId` is a per-message tag, not a per-conversation attribute — a single DM thread can freely mix tagged and untagged messages, and the existing `chat.conversation` query already returns a counterpart's full history unfiltered by `projectId` (verified against `packages/api/src/router/chat.ts`). The web UI does not attempt to partition DM threads by project on this basis: **DMs always render as one continuous, unfiltered thread** wherever DMs are shown, regardless of any project tag on individual messages within them.

Only `Channel.projectId` is a clean, stable boundary — fixed once at channel creation (§5.1.4), inherited by every message in it — so it's what the UI actually uses to decide *where a channel's messages appear*: the dashboard's non-project chat surface vs. a project's own chat panel. A project-tagged DM message stays discoverable via `--project=X` search (§5.1.2); it just isn't pulled into a project's live chat panel or excluded from the dashboard on that basis.

The dashboard's chat surface itself shows **both** DMs and org-wide channels (not DMs alone) — org-wide `Channel`s (§5.1.4/§5.1.10) aren't being retired, just not the dashboard's only content.

### 5.1.10 Single-level `Channel` per project: "project channel" + "issue channels" (Phase 8, done)

Per [ADR-0001](docs/adr/0001-collapse-topic-into-channel.md), the web UI's chat model is one flat level, not Zulip's channel-contains-topics structure (§5.1.4): a `Project` has exactly one auto-created, default **project channel** (`Channel.isDefault`, seeded at `project.create` time the same way `TaskState`'s six defaults are, §5.1.5) plus any number of manually-created **issue channels** for specific discussions — never a channel nested inside another channel. `Channel` remains optionally scoped to a `Project` via `projectId` (`null` = org-wide, unchanged from §5.1.4); within a project, `isDefault` distinguishes the one project channel from its issue channels.

- **`Channel` and `Task` are deliberately not linked.** An issue channel's "issue" is a loosely-scoped discussion topic, not a foreign key to a specific `Task` row — a channel can outlive, precede, or span multiple tasks. Revisit only if a real workflow needs one-click "jump from this task to its discussion".
- **Manual creation only, already true today.** A channel (message container) must be explicitly created before it can be referenced by a message — Padock never adopted Zulip's implicit-topic-materializes-on-send behavior in the first place (verified against `packages/api/src/router/topic.ts`), so this requirement carries forward into the merged model with no new enforcement needed.
- **The project's chat panel has a lightweight channel switcher** (`ChannelPanel`, §5.1.12), not a single fixed feed — it defaults to the project channel, with the project's other issue channels reachable from the same panel.

### 5.1.11 Docs tab: flat list now, nesting is a named future direction (Phase 8, done)

### 5.1.13 Project membership / access control (Phase 9, done)

Every prior phase treated `Project` as visible to the whole org (§5.1.12's "flat Projects list", §5.1.4's "every org member can read every channel"). Phase 9 makes `Project` a real membership boundary via a new `ProjectMember` join (`projectId`, `userId`, `role: admin|member`, unique per pair) — `role` is a separate axis from the org-level `Member.role` (Better Auth's Organization plugin, §5.1.1); being an org admin does not imply project admin.

- **Enforcement point**: a shared `assertProjectMember`/`assertProjectAdmin` helper (`packages/api/src/projectAccess.ts`), called at the top of every project-scoped resolver — `project.list` now filters to `WHERE members.some(userId=caller)` instead of returning every project; `task`/`doc` (both always project-scoped) and `channel`/`chat` (only when project-scoped — org-wide channels stay open, reversing §5.1.4's blanket stance for that one case) all gate reads and writes the same way. A non-member can no longer reach a project's tasks/docs/project-scoped-channel messages just by knowing an id, even though that was previously true (nothing checked it).
- **Project creation** (`project.create`) now sets `Project.createdById` (a field that, oddly, hadn't existed until now despite `Task`/`Doc`/`Channel` all having one) and auto-inserts the creator as `admin` — the only way to become a project's first member.
- **Membership management** (`project.listMembers`/`addMember`/`removeMember`) is admin-only for the latter two, surfaced in the web UI on a new project Overview page (below) and via CLI (`padock project members/add-member/remove-member`, mirrored as MCP tools). Both `removeMember` and demoting a member's role via `addMember`'s upsert refuse to leave a project with zero admins (`assertKeepsAnAdmin`) — an admin-less project could never have its membership managed again.
- **Migration backfilled every existing (`Project`, `User`) pair as `role: admin`** so turning on this filtering didn't lock anyone out of dogfood data that was previously visible to the whole org — same "preserve real data, don't just reshape columns" discipline as the Channel/Topic collapse migration (§5.1.6). Going forward, only a project's creator (then whoever an admin adds) is a member; the backfill was a one-time transition, not the new default.
- **Real bug found via manual testing, not hypothetical**: before the "can't leave zero admins" guard existed for the *demote* path (only the *delete* path had it initially), and before the web UI hid the remove-self button, testing the Overview page by clicking through remove buttons removed the tester's own membership from two dogfood projects — every subsequent action on that page (including just re-loading the member list) then correctly failed with "Not a member of this project," which was surprising in the moment but is exactly the access control working as designed. Fixed three ways: the demote-path guard now mirrors the delete-path one; the web UI never renders a remove button on the caller's own row; and mutation failures render as an inline banner instead of only an unhandled promise rejection in devtools (the previous silent-failure UX is what made the lockout confusing to diagnose).
- **`TaskAssignee` (§5.1.14) points at `ProjectMember`, not `User`, directly** — being assignable to a project's tasks requires already being a member of it. The invariant "an assignee's `ProjectMember` belongs to the same project as the task" is enforced at the API layer (resolving given user ids against that project's own members, rejecting anyone not found), not the schema — Prisma has no cross-table CHECK constraint to express it directly, same precedent as `ChatMessage`'s DM-vs-channel exclusivity (§5.1's original design).

### 5.1.14 Task model deepened: priority, dates, multi-assignee (Phase 9, done)

`Task` (still Phase 1's minimal shape as of §5.1.5 — no priority/dates/assignee) gained three additive fields, all nullable or defaulted so the migration needed no backfill:

- **`priority`**: a `TaskPriority` enum (`urgent`/`high`/`medium`/`low`/`none`, Plane's own five-level scheme; `none` is an explicit "no priority set," not a null column, so Board/Table grouping stays simple), default `none`.
- **`startDate`/`endDate`**: nullable `DateTime`, with composite `(projectId, startDate)`/`(projectId, endDate)` indexes for the Calendar/Timeline views' query patterns.
- **`assignees`**: a `TaskAssignee` join table to `ProjectMember` (§5.1.13) — multiple assignees per task, each one required to already be a member of the task's own project.

Every write path (create, and now-separate `updatePriority`/`updateDates`/`updateAssignees` mutations, matching the existing `updateState`'s one-mutation-per-field granularity rather than one big generic `update`) requires the caller to be a `ProjectMember` (§5.1.13). CLI/MCP got matching surfaces (`task priority`/`task dates`/`task assignees`/`task edit` commands and `task_set_priority`/`task_set_dates`/`task_set_assignees`/`task_edit` MCP tools) in the same phase — no CLI-vs-web capability gap was left standing.

### 5.1.16 BlockNote editor + optimistic-lock autosave: Docs, then Task descriptions (done)

Replaces §5.1.12's plain title-input + Markdown `<textarea>` Doc editor. The Doc detail page (`/projects/[id]/docs/[docId]`) now renders **BlockNote** (`@blocknote/core`/`@blocknote/react`/`@blocknote/shadcn`) as the block-style editing surface — closest available open-source match to Notion's own editing feel — with debounce autosave (1.5s idle) replacing the manual Save button. The same editor + autosave pattern was then extended to `Task.description` (previously a plain `<Textarea>`, save-on-blur, in the Task Detail Modal, §5.1.15) — both are plain-Markdown-backed fields, so the same approach applies unchanged.

- **BlockNote is a view/edit layer only — storage stays plain Markdown (`Doc.blocks`' mdast, §5.1.7; `Task.description`'s plain `String?`), never BlockNote's own block JSON.** Considered and rejected: storing BlockNote's native block schema directly, which would avoid a parse/serialize step on every load/save. Rejected because BlockNote's block JSON is an unversioned internal representation of a fast-moving third-party package, not a stable spec the way mdast/remark is — coupling self-hosted, long-lived data to it would tie every future `@blocknote/core` upgrade to a possible data migration, a cost Markdown's stability doesn't carry. It would also invert Padock's own agent-first premise (§1/§5.1.3): Markdown would become a lossy derivative of the true stored state instead of being the state itself. The API is unchanged as a result — `doc.ts`/`task.ts` still only ever emit/accept Markdown `content`/`description`; conversion (`tryParseMarkdownToBlocks`/`blocksToMarkdownLossy`) happens entirely inside the web UI at the load/save boundary — once per open, once per debounce tick, not per keystroke — via a shared `MarkdownEditorView` component (`apps/web/src/components/`) so the BlockNote wiring (and the SSR workaround below) exists exactly once, not once per entity.
- **A custom editor engine (hand-rolled ProseMirror/contentEditable) was considered and rejected.** Taming `contentEditable` — selection across blocks, IME composition, paste sanitization, undo/redo — is the specific, well-known hard problem ProseMirror itself exists to solve; Plane (§0's own named reference) builds its Pages editor on Tiptap rather than a bespoke engine for the same reason. Because the editor is already just a swappable view layer over Markdown (previous bullet), there's no lock-in cost to depending on a library here, so there was no offsetting reason to pay that cost.
- **Optimistic locking on `doc.update`/`task.update`**: a new optional `expectedUpdatedAt` input on each — when provided and it doesn't match the row's current `updatedAt`, the mutation throws `TRPCError({ code: "CONFLICT" })` instead of silently overwriting. The web UI's autosave always sends it, surfacing a "this content changed elsewhere" banner on conflict with an explicit reload-vs-overwrite choice (shared `AutosaveStatus` component) — neither side's edits are ever discarded without the user choosing that. CLI/MCP callers omit it, preserving today's fire-and-forget write behavior for agents. This still covers the motivating scenario — a human editing in the browser while an agent writes the same row via CLI concurrently — because it's the *browser's* next autosave tick that carries a now-stale `expectedUpdatedAt` and gets caught; only two agents racing each other with neither specifying the field stays unprotected, which is pre-existing behavior, not a new regression.
- **Task's lock ref is shared across every field that touches `Task.updatedAt`, not just description.** The Task Detail Modal also has immediate-mutation controls alongside the description editor — state/priority/date `<Select>`s (§5.1.15) — each of which bumps `Task.updatedAt` the same as a description save would. If those kept their own independent `expectedUpdatedAt` bookkeeping (or none), changing priority while the description autosave was mid-flight would make the *next* description autosave spuriously conflict against a change the same user just made. Fixed by having `changeState`/`changePriority`/`changeDates` all funnel their mutation's returned `updatedAt` back into the same ref the description editor's save/conflict logic reads — confirmed by a real test (Playwright: change priority while a description edit is debounce-pending, assert no conflict banner appears). `updateAssignees`/`updateLabels` don't need this — they write `TaskAssignee`/`TaskLabel` rows, not `Task` itself, so they never touch `Task.updatedAt`.
- **Verified in a real browser, not just typecheck** — Playwright driving a throwaway registered user end to end (create project → create doc/task → type → confirm live style conversion, not raw Markdown text → wait for debounce autosave → reload → confirm persistence; two tabs on the same doc to confirm the conflict banner fires and neither tab's edits are silently discarded). This is the first Doc/Task UI work in the project verified this way — §5.1.12/§5.1.15 both explicitly recorded no browser-automation tool being available in the sessions that built them.
- **Found and fixed by that verification, not by inspection**: BlockNote (ProseMirror underneath) touches `window`/`document` on init, which crashed Next's server-render pass with `window is not defined` even though the page is `"use client"` — App Router still SSRs the initial HTML for client components unless SSR is explicitly disabled for them. Fixed by loading the BlockNote-containing component via `next/dynamic({ ssr: false })`.

### 5.1.17 Doc creation: no title dialog, create-then-edit; manual delete added (done)

"New doc" no longer opens a dialog asking for a title first (§5.1.16's-era flow) — clicking it immediately calls `doc.create` with `title: "Untitled"`, `content: ""` and navigates straight into the editor, matching how every comparable real-time-autosave editor actually behaves (Notion, Google Docs, Confluence, Medium all create a real row immediately on "new document" and let the user type into it, rather than deferring persistence until the first keystroke) — considered and rejected a purely client-side draft (create only on first real edit, swapping the URL from a placeholder route to the real one afterward): it avoids ever writing an abandoned-empty row, but no major product actually does this for a live-autosave editor, and the win doesn't offset the real cost — a create-then-URL-swap transition that has to keep the editor instance alive without remounting, race against the debounce firing mid-swap, and behave sanely on back/forward navigation.

- **`title: "Untitled"`, not an empty string** — `Doc.title` is a non-nullable `String` column; giving every fresh doc a real, non-empty value avoids a special empty-string case anywhere titles are displayed, sorted, or (eventually) searched.
- **No auto-cleanup of abandoned empty docs.** An untouched "Untitled" doc is left in place rather than deleted on navigate-away/tab-close — deliberately simplified: browsers don't guarantee an async delete call fired from `beforeunload` actually reaches the server, so a "delete on leave" mechanism would only ever be best-effort, not the guarantee it sounds like. Manual deletion (below) is the v1 answer; an opportunistic or scheduled sweep for untouched empty docs is a named future optimization, not built now.
- **`doc.delete` (new)**: project-member-scoped write, takes an optional `expectedUpdatedAt` — same optimistic-lock shape as `doc.update` (§5.1.16), protecting against deleting a doc that was edited more recently than whoever clicked delete last saw (the web UI's Docs list and detail page always send the `updatedAt` they currently have on hand; CLI/MCP omit it, consistent with §5.1.16's "agents don't lock by default" stance). Exposed via CLI and MCP alongside `doc create/list/get/update` — no special reason to withhold it from agents: an unattended agent's delete is already gated through the same approval queue (`runOrQueue`) every other write goes through, so it carries no new risk create/update don't already carry.
- **`doc.update` distinguishes "the doc no longer exists" from a version conflict.** If the row was deleted out from under an open editor (the lock in the previous bullet only catches deletes that happen *after* the deleter's own `updatedAt` was current — a delete that races in before the editor's first autosave isn't caught by any lock), the next autosave attempt gets a distinct not-found error, not the reload-vs-overwrite conflict banner — there's nothing to "reload" once the doc is truly gone, so the recovery UI has to be different: a plain "this doc was deleted, your changes weren't saved" message.
- **Delete has a confirmation dialog** (built with the existing `Dialog` primitive, no new shadcn component installed for it), on both the Docs list (per-row) and the detail/editor page — unlike the existing no-confirmation Label-delete precedent (Overview page), because losing an entire document's content is higher-stakes than un-tagging a label, and there's no trash/undo to fall back on.

### 5.1.18 Doc custom attributes: project-scoped schema, EAV storage (planned)

Notion-style custom properties on `Doc`, decided via a grilling session rather than shipping the closest existing precedent (`Task.labels`/`TaskState`) unmodified — neither fit: `Label` is a flat many-to-many tag, `TaskState` is a single fixed-shape per-project enum, and what's wanted here is an arbitrary, per-project-defined set of *typed* fields (text/number/select/date/checkbox), which neither precedent's shape covers.

- **Schema is project-scoped, not per-doc.** A project defines a set of `DocAttributeDefinition`s once (name + type, `@@unique([projectId, name])`); every `Doc` in that project shares the same attribute schema and fills in its own values. Rejected: fully ad-hoc per-doc fields — no cross-doc consistency, and nothing to build a table/filter view against later, unlike a shared schema.
- **No attributes ship pre-defined.** Unlike `TaskState`'s six seeded defaults, a fresh project starts with zero doc attributes; every one is user-created. There's no universally-right default set for an arbitrary-document-type feature the way there is for task workflow states.
- **Storage is a dedicated EAV shape, not a JSON column on `Doc`.** Three new tables: `DocAttributeDefinition` (`projectId, name, type, order`), `DocAttributeOption` (select-type choices only — `definitionId, name, color, order`, its own table rather than reusing `Label`, since overloading `Label`'s meaning to double as generic select-options would blur what a "label" is), and `DocAttributeValue` (one typed column per possible type — `valueText`/`valueNumber`/`valueDate`/`valueBoolean`/`selectOptionId` — `@@unique([docId, definitionId])`). Chosen over a single `Json` column on `Doc` specifically so Postgres can enforce real column types and referential integrity (FK to the option row, cascade deletes) rather than pushing all validation into the API/Zod layer, matching this codebase's existing strongly-typed-schema convention (every other relation is a real FK, not a loosely-typed blob).
- **A definition's `type` is immutable after creation.** Changing `text` → `number` on a definition that already has values would require either a lossy conversion or an ad-hoc cleanup step; simpler to require deleting and recreating the definition instead. Renaming, reordering, and (for `select`) managing options remain freely editable.
- **Deleting a definition (or a select option) cascades**: every `DocAttributeValue` row referencing it is deleted along with it (DB-level `onDelete: Cascade`), matching the existing `Label`→`TaskLabel` delete precedent. No soft-delete/undo.
- **New definitions don't backfill existing docs.** A `DocAttributeValue` row is only created when a value is actually set; a doc with nothing filled in for a given attribute simply has no row for it, and the UI shows it as empty. No "required" flag exists — every attribute is optional, keeping this consistent (a required flag would immediately put every pre-existing doc in a permanently-incomplete state).
- **`select` is single-value only** (`selectOptionId` is a single nullable FK, not a join table) — multi-select tagging is a possible future extension but wasn't requested; the schema would need `DocAttributeValue`↔`DocAttributeOption` to become many-to-many if it is.
- **`date` is date-only, no time component** — matches the `due date` mental model this is expected to be used for; a `datetime` variant is a future extension if a real need for time-of-day precision shows up.
- **Values save immediately per-field, not via the doc editor's shared debounce/lock.** Unlike `title`/`content` (§5.1.16, one debounced `save()` sharing a single `knownUpdatedAt` optimistic-lock ref), each attribute-value edit fires its own mutation on commit (blur for text/number, on-select for select/date/checkbox) — deliberately *not* funneled into the title/content lock ref, since attribute edits are typically one discrete action at a time (pick a date, toggle a box) rather than continuous typing, so debouncing them would only add latency without protecting against anything real.
- **Schema management UI lives on the existing Project Overview page** (`/projects/[id]/overview`, §5.1.13's membership-management page), not a new `/settings` route — this codebase has no project-settings page at all yet, and Overview is already the project's one page for project-level (not doc-level) configuration. Any project member can create/rename/reorder/delete definitions and options — no admin-only restriction, consistent with how Overview's existing Label management already works.
- **Value-editing UI lives on the Doc detail page** (`/projects/[id]/docs/[docId]`) as a new property panel, one row per defined attribute, rendered with the type-appropriate control. Deliberately **not** added to the Docs list view this round — a table/column view over attributes is a real feature (sortable/filterable columns) that deserves its own scoping pass, not a byproduct of this one.
- **All definition/option/value mutations go through `runOrQueue`**, same as every other doc write (§5.1.1/§6's approval-queue mechanism) — no special-casing; an unattended agent setting a doc attribute is exactly as reviewable as it setting the title.
- **Explicit scope cuts this round** (deviating from Phase 9's closing note that CLI/MCP got "no capability gap left" — §5.1.14/§5.1.15): CLI/MCP support for defining/reading/writing doc attributes is deferred, web-only for now; filtering/searching docs by attribute value (`doc.list`/`search.ts`) is also out of scope. Both are named gaps, not oversights — tracked in §7.

### 5.1.19 Cross-domain notification system (planned)

Decided via a grilling session, not shipped yet. Goes beyond §7's narrow "approval queue notifications" gap — a general `Notification` model with pluggable trigger points across domains, not a one-off for `/approvals`.

- **Recipient is always a `User`, never a PAT/agent identity.** An agent acts on behalf of a `User` (its owning PAT's holder); it isn't an independent addressable actor with its own inbox, and already has its own pull mechanism (`padock approvals status`/`list`) for the one thing it currently needs to check. Whoever *triggered* an event (human or unattended agent) is tracked separately (`Notification.actorId`) from whoever *receives* it (`Notification.userId`) — the two are not the same axis.
- **v1 trigger events** (deliberately narrow — only where the recipient is already unambiguous from existing domain relationships, no `@mention`-style parsing): `TaskAssignee` create (you were assigned a task), `ProjectMember` create (you were added to a project), `ChatMessage` DM send (you received a point-to-point message). Doc changes, channel activity, and approval-queue events are named but not built this round — the same "revisit once a real trigger is needed" posture as §7's other deferred items.
- **Schema: nullable FK per trigger type, not generic `entityType`/`entityId`.** Follows §5.1.18's `DocAttributeValue` precedent (real Postgres FKs + `onDelete: Cascade`, not a loosely-typed polymorphic reference validated only in the API layer) over `ChatMessage`'s own DM-vs-channel exclusivity pattern (multiple nullable FKs, mutual exclusivity enforced at the API layer since Prisma has no cross-table CHECK). Cost: every future trigger type (e.g. doc changes) needs its own new nullable FK column and a migration — accepted, consistent with this project's `prisma migrate`-first workflow (§5.1.6) rather than reaching for a schema-avoiding generic column.
- **Realtime delivery is targeted per-user, a deliberate deviation from §5.1.4's unfiltered chat broadcast** — see [ADR-0002](docs/adr/0002-targeted-notification-delivery.md). `apps/realtime` gains a `userId → Set<WebSocket>` connection registry (today's flat `Set<WebSocket>` only tracks connections, not identity, even though `resolveIdentity` already resolves `user.id` per connection). `packages/api`'s `publishEvent` envelope is generalized to `{ type, recipientUserIds: string[] | "broadcast", payload }`; chat's existing calls keep passing `"broadcast"` unchanged (zero behavior change there), notifications always pass the single recipient's `userId`. "Who should receive this" is resolved in `packages/api` (business logic), `apps/realtime` only routes on `recipientUserIds` — keeping the no-business-logic-in-realtime rule (§5.1) intact.
- **The WebSocket push is best-effort only; the `Notification` row in Postgres is the durability source of truth.** Created synchronously in the same write path as the triggering mutation (inside a shared `notify()` helper, below), regardless of whether the recipient is currently connected. A disconnected recipient's push is simply not sent — never queued or retried at the `apps/realtime`/Redis layer, since the DB row already guarantees nothing is lost. On mount and on every WebSocket reconnect, the client calls `notification.unreadCount` to compute the badge from the DB directly, independent of how many pushes it did or didn't receive while away.
- **Marking a notification read re-broadcasts to the same user's other connections.** `notification.markRead` writes `isRead`/`readAt`, then publishes `{ type: "notification.read", recipientUserIds: [userId], payload: { notificationId } }` through the same targeted mechanism, so every open tab/device for that user (not just the one that clicked) updates its local unread count immediately instead of drifting until each tab's next independent refetch.
- **A shared `notify()` helper (`packages/api/src/notify.ts`), not three inline implementations.** Matches this codebase's standing convention of extracting repeated cross-cutting logic (`assertProjectMember`/`assertProjectAdmin` in `projectAccess.ts`, `runOrQueue` in `approvalGate.ts`, `publishEvent` in `redis.ts`) instead of duplicating it per call site. All three v1 triggers call it; a future trigger is one more call, not a new copy of the write+publish logic. Because `runOrQueue` already short-circuits an unattended agent's queued (not-yet-approved) write before the resolver body's real logic runs, placing the `notify()` call after that check means a merely-queued action never fires a premature notification — no extra handling needed for that interaction.
- **`notification.list` is the first real cursor-paginated query in this codebase — a deliberate deviation, not an oversight.** Every existing list query (`chat.inbox`'s `take: 200`, `approval.list`'s `take: 50`) is a flat "sort and truncate" with no cursor/offset mechanism at all. `notification.list` breaks that precedent on purpose: `{ cursor?: string, limit: number }` in, `{ items, nextCursor }` out, standard Prisma `cursor`+`skip: 1`+`take: limit + 1` shape. `notification.unreadCount` stays a genuinely separate `count()` query (`where: { userId, isRead: false }`) rather than being derived from whatever page of `list` happens to be loaded — deriving it from a capped page would silently under-count once a user has more unread items than one page holds, undermining the §5.1.19 badge-correctness guarantee above.
- **Web UI: a bell icon in the persistent top header** (`apps/web/src/app/(app)/layout.tsx`'s `<header>`, next to the session email/sign-out), not inside `AppSidebar`. The header is the one chrome element that's never collapsed to zero width (unlike `AppSidebar`, which the user can collapse via `leftCollapsed`) — putting the bell there means it's visible from every page regardless of sidebar state. Clicking it opens a small popover showing the first page of `notification.list` (reusing the same cursor query, not a separate "recent" endpoint) with a "view all" link to a full `/notifications` page for anything beyond that — not a direct navigation-only pattern like `/approvals`, since checking notifications is a much higher-frequency, lower-friction action than reviewing a queued approval.

### 5.1.20 Chat mention: `@user` / `#task` / `#doc` (planned)

Decided via a grilling session, not shipped yet. Extends chat (§5.1.9/§5.1.10) with inline references to people, tasks, and docs — the first feature that connects all three domains from *within* a single chat message, not just via `--project=X` search (§5.1.2).

- **Structured tokens, not free-text name matching.** `ChatMessage.content` stores mention targets as typed tokens (`@[user:id]`, `#[task:id]`, `#[doc:id]`) rather than regex-matching `@SomeName` against the user table — name-matching breaks on duplicate names and renames, and can't back a stable id for `notify()` to target. Rejected specifically because it can't survive a rename.
- **Token is id-only, no embedded name/title snapshot.** Rejected embedding a display name in the token itself (e.g. `@[user:id:Alice]`): a stale snapshot would keep showing a pre-rename name forever, and names/titles can contain the token's own delimiter characters (`]`, `:`), which would make the parser fragile. Display text is resolved live at read time instead (next bullet).
- **A dedicated `ChatMention` join table** (`chatMessageId`, `targetType`, `targetId`) is written alongside `content` at send time — the same "real FK table over embedding data in a blob" precedent as `DocAttributeValue` (§5.1.18) over a `Json` column. `content`'s job is display reconstruction; `ChatMention`'s job is every query that needs to know "who/what was mentioned" — `notify()` fan-out, and future backlink features ("every message that references this task") a content-string parse can't support efficiently.
- **Two trigger keys, not three, and not one merged picker.** `@` is reserved for people only (keeps the "I'm calling this person" intuition undiluted); `#` is shared by both `task` and `doc`. Rejected a fully merged `@`-triggers-everything picker (dilutes the person-calling intuition) and a fully split three-symbol scheme (a third symbol adds a third trigger-detection code path and something to remember, for a payoff `#` already covers by grouping). The `#` dropdown is one live-searched list with "Tasks"/"Docs" section headers, not a two-step category-then-search flow — a two-step flow adds friction when the user already knows the target's name.
- **`#` search is a new server-side tRPC procedure, not the client-side full-list-filter pattern `user.list`/`project.listMembers` use today** (`chat-right-sidebar.tsx`'s `matchesQuery`, §5.1.13). Task/doc counts scale with project activity in a way org user counts don't — the "fetch everything, filter in the browser" pattern would degrade on any active project. Search resolves against a project anchor first (`Channel.projectId` when set), falling back to the sender's own `ProjectMember` memberships across all their projects (cross-project results carry a project-name badge) only when the conversation has no project anchor (a global channel, or a DM with no `project_id` tag).
- **`@user` candidates are scoped to who can already see the conversation**, not an org-wide list — a project-scoped channel offers only that project's members, a global channel offers the whole org (matching its existing open-read model, §5.1.4), a DM offers only the other participant. Rejected leaving the candidate list org-wide and letting a bad mention 404 on click: a notification pointing at content the recipient can't open is a worse failure here than at the picker stage, since it's the whole conversation that's inaccessible, not just one linked entity.
- **Read-time permission filtering on `#task`/`#doc` chip resolution — closes a leak the compose-time restriction above doesn't cover.** Compose-time scoping (previous bullet) only restricts what the *sender* can pick, not who can later *read* the message; a global channel is open to the whole org, so a task mentioned from a project the sender belongs to can still render its title to a reader who isn't a member of that project. Since `assertProjectMember` (§5.1.13) already gates direct task/doc reads, the same check applies when batch-resolving mention titles for message-list rendering — a non-member reader gets an anonymized placeholder in place of the real title, rather than the resolver short-circuiting the whole message. This is a per-viewer result: two readers of the same global-channel message can see different resolved text for the same token.
- **Only `@user` triggers `notify()` (§5.1.19); `#task`/`#doc` are link-only, never notify anyone** — rejected also notifying a mentioned task's assignee(s), specifically to avoid notification fatigue: `#task` references are common, casual, incidental ("this relates to #142") in a way `@user` is not, and assignee-notify-on-reference would turn every passing reference into a ping. One new `NotificationType.chat_mention` value, not split DM/channel variants — `Notification.chatMessageId` (already the FK, §5.1.19) is enough to recover context, the same reasoning that kept `chat_dm` unsplit. Multiple mentions of the same user within one message collapse to one notification and one `ChatMention` row; self-mention is already suppressed by `notify()`'s existing `actorId === userId` check, no new handling needed.
- **Composer upgraded from a plain `<Textarea>` (§5.1.9, `chat-thread.tsx`) to `contentEditable`, via `@tiptap/react` + `@tiptap/starter-kit` (minimal config: paragraph/text only, no block features) + `@tiptap/extension-mention`.** A deliberate UX-over-caution call: a mirror-div-positioned dropdown over a plain `<textarea>` (lower implementation risk, zero IME exposure since the textarea's native composition handling is never touched) was the initially-recommended path, overridden in favor of live inline-chip rendering while composing. Rejected reusing BlockNote (§5.1.16, already a dependency): it's a full block-document editor, the wrong shape for a one-line/few-line chat compose box, and coercing it down risks breaking on future `@blocknote/core` upgrades. Rejected hand-rolled `contentEditable` + manual Selection API (§5.1.16's own precedent for the same rejection, on the doc/task editors): IME composition is the specific hard problem a hand-rolled approach reliably gets wrong, a real risk given Padock's own usage includes Traditional Chinese IME input. `@tiptap/extension-mention` is purpose-built for exactly this "trigger char → suggestion list → inline node" shape and natively supports multiple trigger-char configs, matching the two-trigger-key decision above.
- **Scope: `@user`/`#task`/`#doc` ship together in one pass**, not `@user` first with task/doc deferred — the token format was already made generic (`type`-tagged) specifically so a later type wouldn't need a breaking format change; given that, the marginal cost of building all three pickers/resolvers now was judged lower than the cost of a second pass later.
- **No message-edit interaction to design.** Chat (`packages/api/src/router/chat.ts`) has no edit/delete mutation yet, only send/read, so "mentions changing on edit" isn't a live concern; existing pre-feature messages are unaffected — no tokens, no `ChatMention` rows, render exactly as before.

### 5.2 Padock CLI

The actual engine that agents drive. One consistent command grammar across all three domains, e.g.:

```
padock search "<query>" --scope=docs,tasks,chat --project=<name>
padock doc get <id>
padock task update <id> --status=review
padock chat send --to=<user|channel> --message="..."
padock whoami / padock login   # auth against a running Padock instance
```

The CLI is the single implementation of "how to talk to Padock." Everything above it (MCP server, the Skill's instructions — §5.3) is a thin adapter, not a reimplementation.

### 5.3 Skill layer — one portable SKILL.md, not per-agent adapters

**Agent Skills (the `SKILL.md` format) is a cross-vendor open standard, not a Claude-only mechanism** — published at agentskills.io in December 2025, adopted within 48 hours by OpenAI and Microsoft, and natively supported by Claude Code, Codex CLI, Gemini CLI, Cursor, GitHub Copilot, and 35+ other tools as of mid-2026. As long as a `SKILL.md` sticks to the *core* spec — `name`/`description` frontmatter + a Markdown instruction body, no tool-specific frontmatter extensions — the same file works unmodified across all of them. This changes the design from "build Claude's adapter first, generalize later" to: **write one Skill, distribute it to every discovery path.**

- **Content**: one `SKILL.md` documenting the CLI's command grammar (§5.2) and trigger phrases — teaches any agent when and how to shell out to `padock`. No agent-specific variants; if a tool-specific extension is ever needed for one platform, it's additive (tools ignore fields they don't recognize) and doesn't fork the file.
- **Discovery paths differ per tool, even though the file doesn't** — `padock init-skill` writes the identical `SKILL.md` to each known location:
  - `.agents/skills/padock/` (repo-level) — scanned directly by **Codex CLI** and aliased by **Gemini CLI** (`.gemini/skills/` treats `.agents/skills/` as an alias)
  - `~/.agents/skills/padock/` (user-level) — same alias relationship, covers both tools' user-tier scan
  - `~/.claude/skills/padock/` — **Claude Code**'s own convention; not confirmed to alias `.agents/skills/`, so it gets its own copy
  - Three file writes of one identical source, not three different packages.
- **Distribution (v1)**: ships as part of the `padock` CLI package, not a separate marketplace/registry. `padock init-skill` writes the version-matched `SKILL.md` to the paths above. Keeps the Skill in lockstep with the CLI's command grammar automatically; avoids a second release/review pipeline before the project has external users. Publishing to agentskills.io or an official marketplace is a later distribution optimization, not a v1 requirement.
- **MCP server wrapper — done (Phase 5)**: `padock mcp serve` starts an MCP server (stdio transport, verified against the real `@modelcontextprotocol/sdk` v1.30.0) exposing the full command grammar as ~20 tools, one per CLI subcommand (`project_create`, `task_update`, `chat_send`, `search`, ...) plus `whoami`. Not a second implementation — every tool calls the same `actions/*.ts` functions the CLI commands themselves call (extracted specifically so there'd be exactly one implementation, not a CLI copy and an MCP copy); reuses the same `~/.config/padock/` login, no separate auth. `login`/`init-skill` are deliberately **not** tools — they're one-time human setup steps, not part of the day-to-day grammar an agent drives. Not required for cross-agent reach (the Skill format already solved that, above) — this is purely an optional richer transport for MCP-capable clients that would otherwise have to shell-parse the CLI's stdout.
- **Still open**: publishing the Skill to agentskills.io or an official marketplace — a real external/public action requiring a human decision on timing, not engineering work, so it stays unscheduled rather than being treated as "not started yet."

## 7. Open decisions (deferred, not blocking Phase 0–3)

- **Finer-grained PAT scopes** (per-project, per-action-verb beyond read/write): Phase 6 shipped per-domain read/write only. Revisit if a real use case needs narrower slicing (e.g. a key scoped to one specific project, not the whole `task`/`doc` domain).
- **Approval queue notifications/expiry**: Phase 6b's `/approvals` page is pull-only (a human has to go check it) — no push notification (email/chat ping) when something new is queued, and no expiry/TTL on a pending request that never gets decided. §5.1.19's planned Notification system does **not** cover this in v1 either — a new `ApprovalRequest` isn't one of the three v1 triggers — so this gap stays open even once notifications ship; wiring approval-queue events into `notify()` is the natural next trigger to add, not a rebuild.
- **Enterprise directory login (LDAP/AD)**: no official Better Auth LDAP plugin exists (§5.1.1). Near-term path is the SSO plugin (SAML/OIDC) fronting the directory via an IdP; revisit raw LDAP bind only if a real deployment proves the SSO path insufficient.
- **Web UI gaps left by Phase 8** (§5.1.12): no "start a new DM" composer on the Dashboard (only conversations with existing history show up); no delete/archive for tasks, docs, or channels; the doc editor is a plain Markdown textarea, not the Notion-level rich/nested editor named as the long-term direction (§5.1.11). None of these block §8's north star (already CLI/MCP-complete); revisit as real usage surfaces friction.
- **Web UI gaps left by Phase 9** (§5.1.15): the New Task dialog only takes title/description at creation time — priority/dates/assignees have to be set afterward via the Task Detail Modal, not inline at creation. Timeline is view-only (no drag to resize/move a bar, unlike Board/Calendar's drag-to-change-state/date) — an explicit scope call for this round, not a limitation of the layout itself. Neither blocks the assign-a-task workflow this phase was built for.
- **Finer-grained project access control**: Phase 9's `ProjectMember` model (§5.1.13) is binary (member or not) plus one role axis (admin/member) — no per-resource permissions within a project (e.g. "can view tasks but not docs"), and no bulk/CSV member import. Revisit if a real project needs narrower slicing than "in the project" vs "not."
- **Doc custom attributes gaps** (§5.1.18): CLI/MCP support (define/read/write attributes) wasn't built alongside the web UI, reopening the capability gap Phase 9 had just closed — revisit once web usage validates the schema shape. Filtering/sorting the Docs list by attribute value, and showing attributes as list columns, are also deferred — this round only covers display/edit on the Doc detail page. `select` attributes are single-value only; multi-select is a possible future extension if tagging-style usage shows up.

## 8. Example end-to-end flow (north star scenario)

> "幫我去某某專案找某某資料，整理分析完之後告訴我，確認沒問題請幫我發給某某同事，然後把任務狀態改成 review。"

1. Agent (via Skill, running interactively with the user present) calls `padock search "某某資料" --project=某某專案` → full-text search hits docs + tasks (always project-scoped) + any chat DMs previously tagged with that `project_id` (§5.1.2), in one query.
2. Agent reads/analyzes returned content itself (Padock returns raw matches, not a semantic summary — §5.1.3) and reports findings back to the user in the same conversation.
3. User confirms ("沒問題") — this *is* the confirm-before-act step (§4) for an interactive agent. (An unattended/scheduled agent running the same flow would instead have steps 4–5 queue on `/approvals` for a human to decide later — Phase 6b, §5.1.1.)
4. Agent calls `padock chat send --to=同事 --message="<analysis summary>"` (point-to-point DM — §5.1.3).
5. Agent calls `padock task update <id> --status=review` (one of the four fixed statuses — §5.1.3).
6. Every step above is attributed to the agent + user (via the PAT used) in Padock's audit log.

This flow is the acceptance test for the MVP: if it can't run end-to-end (even with minimal features in each domain), the MVP isn't done.

## 9. Proposed phasing (tracer-bullet, not deep-then-deep)

Build a thin walking skeleton across all three domains first, validate the flow in §8 end-to-end, then deepen each domain — rather than fully building one domain before starting the next.

1. **Phase 0 — Platform skeleton**: Turborepo scaffold, auth (Better Auth + API Key/Organization plugins, dual-track cookie/bearer), `Project` entity, Postgres+Redis+storage wiring, docker-compose (`app`/`realtime`/`worker` roles).
2. **Phase 1 — Thin vertical slice**: DM-only chat, fixed-enum task status, Markdown docs — all Project-scoped per §5.1.2–5.1.3 — enough for §8 to run manually via the web UI / direct API calls.
3. **Phase 2 — Padock CLI**: implement the command grammar in §5.2 (incl. `padock login` manual-token flow, `tsvector` search) against the Phase 1 API.
4. **Phase 3 — Universal Agent Skill**: one portable `SKILL.md` (§5.3, the open Agent Skills standard — no per-agent adapters needed), `padock init-skill` distributing it to Claude Code/Codex CLI/Gemini CLI's discovery paths in one shot; dogfeed the §8 scenario end-to-end with a real subscription agent (Claude Code, since that's the maintainer's daily driver — §6 first validation target), but the artifact itself isn't Claude-specific.
5. **Phase 4 — Deepen each domain** — **done**: channels/threads for chat (§5.1.4), configurable workflows for tasks (§5.1.5), block-based doc storage (§5.1.7), plus the switch to `prisma migrate` (§5.1.6) that came out of doing this with live dogfood data. Sequenced one slice at a time rather than simultaneously, per this session's choice.
6. **Phase 5 — Optional richer transport & marketplace distribution**: MCP server wrapper (`padock mcp serve`) — **done**, §5.3. Publishing to agentskills.io/an official marketplace is still open — a human/business decision, not engineering work.
7. **Phase 6 — Non-interactive agents & fine-grained permissions** — **done**: PAT granular scopes (per-domain read/write, §5.1.1/§6, Phase 6) and a server-side approval queue for unattended/scheduled agents (§5.1.1/§6, Phase 6b) — both shipped. Notifications/expiry on the approval queue remain open (§7), not blocking.
8. **Phase 7 — Web UI shell** — **done**: landing page, login/register auth flow, `proxy.ts` route protection, authenticated app shell wrapping `/dashboard` (placeholder) and `/approvals` (§5.1.8). Chat/task/doc web views are still not built — those domains remain CLI/MCP-only (§7).
9. **Phase 8 — Chat/task/doc web UI** — **done**: collapsed the Channel/Topic chat model (ADR-0001, §5.1.10), then built a sidebar-first shell, a real Dashboard (chat feed + project overview), and a project workspace (Task/Docs tabs + collapsible chat panel) (§5.1.12). Remaining gaps (DM composer, delete/archive, rich doc editor) are tracked in §7, not blocking.
10. **Phase 9 — Project access control + deepened task model + multi-view task UI** — **done**: `ProjectMember` (§5.1.13) turned `Project` into a real membership boundary — gates `project.list` and every task/doc/project-scoped-channel/chat read-write, reversing §5.1.4's "every org member reads every channel" for project-scoped channels specifically (org-wide stays open). `Task` gained `priority`/`startDate`/`endDate`/multi-`assignee` (§5.1.14, assignees scoped to `ProjectMember` not bare `User`). The Task tab gained a List/Board/Table/Calendar/Timeline view switcher plus a shared Task Detail Modal for editing (§5.1.15), and a new project Overview page for membership management. CLI/MCP got matching surfaces for all of it in the same phase — no capability gap left between web and CLI/MCP.

## 10. Non-goals (v1)

- No third-party SaaS integrations (Slack/Notion/Jira/etc.) — explicitly out of scope; Padock is the tool, not a connector hub.
- No multi-tenant SaaS hosting.
- No full realtime multi-cursor collaborative document editing in v1 (decided in §6: single-user editing + version history first; CRDT later, transport designed to accommodate it).
- No semantic/vector search in v1 (§5.1.3, §6) — full-text only, to avoid an embedding-model dependency.
- No push notifications or expiry on the Phase 6b approval queue (§7) — pull-only, unbounded pending requests until a human checks `/approvals`.
- No per-resource-instance PAT scoping in v1 (§7) — Phase 6 shipped per-domain read/write; per-project or finer slicing is deferred.
- No raw LDAP bind in v1 (§5.1.1, §7) — enterprise SSO (SAML/OIDC via Better Auth's SSO plugin) is the supported enterprise-auth path; direct LDAP only if later proven necessary.
- No marketplace/registry publishing of the Skill (§5.3) — a human/business timing decision, not engineering work.
