# Collapse `Topic` into `Channel` — single-level chat containment, not Zulip's two-level stream+topic

Phase 4 (CONTEXT.md §5.1.4) adopted Zulip's stream+topic model: a `Channel` groups many `Topic`s, and every channel message belongs to exactly one `Topic` (`ChatMessage.channelId` + `topicId`, both required). While planning the Phase 8 web UI, this stopped matching the product's actual mental model — a `Project` should have one auto-created default "project channel" plus manually-created "issue channels" for specific discussions, a **single** flat level per project, not two. The one property that made Zulip's two-level design worth its complexity — topics materializing implicitly from a free-text string on send — was never actually built in Padock: a `Topic` already requires an explicit `topic.create` call before it can be referenced, so the model's supposed payoff never applied here.

**Decision**: merge `Topic` into `Channel`. The renamed `Channel` entity takes over `Topic`'s old role as the actual message container — each row optionally scoped to a `Project` via `projectId`, with an `isDefault` flag marking a project's auto-created "project channel" (mirroring `TaskState.isDefault`, §5.1.5). The old grouping-level `Channel` table is removed. `ChatMessage` gets a single `channelId`, replacing the previous `channelId`+`topicId` pair.

**Consequences**: this is a breaking change to already-shipped, agent-facing surfaces, not just an internal refactor — `packages/api/src/router/channel.ts`/`topic.ts` merge into one router, the CLI's `padock channel`/`padock topic` commands merge, MCP tools and `SKILL.md` update to match, and any existing dogfood data needs an explicit migration path from old `Channel`+`Topic` pairs into the new flat `Channel` rows (same two-step add/backfill/drop discipline as the Phase 4 `TaskStatus` migration, §5.1.5's migration note).

**Considered and rejected**: keeping the schema as two levels and having the web UI merely *present* a flattened view over it (Topic rows relabeled "Channel" in the UI, old Channel demoted to an invisible auto-managed wrapper). Zero migration cost, zero CLI/MCP impact — but it leaves a permanent mismatch between what the database models and what the product actually means by "Channel," for a savings that only mattered short-term. Decided to pay the migration cost now, while dogfood data is still small, rather than carry the mismatch forward indefinitely.
